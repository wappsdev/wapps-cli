Encoding contract
-----------------
Dispatch, Attach, Progress, Finish, Cancel and Register encode explicit JSON
bodies. Dispatch and Cancel require LeaseAuthority; Attach, Progress and Finish
require JobAuthority. Neither a principal nor a lease is invented by the codec.
Register is an explicit tokenless body, not automatic mission registration.
The existing dependencies serde and serde_json are sufficient.

Dispatch contains exactly authority, laneId, role, dispatchKey, base, head,
task, workerProvider and present workItemId, reviewsJobId, resumesJobId,
answersQuestionId. There is no operationKey on jobs: that key belongs only to
work_add/work_ask. No model, effort, tools, handBack, principal, time, cwd,
local path or worktree metadata can enter dispatch through this API. Worktree
path/branch is an optional attach field, exactly as the cloud declares it.
The cloud validates declared role ceilings and one-bind admission. Local
routing/review independence remains pending slice 13.3 runtime integration;
this encoder does not enforce either policy.

Optional outbound fields are omitted, not emitted as null. Finish accepts an
explicit empty output/error and does not trim either. Trimmed fields follow
JavaScript trim (BOM is whitespace; NEL is not) and UTF-16 unit ceilings.
Over-limit or empty trimmed inputs produce Protocol; they are not truncated or
filled with defaults. Mission ids follow the ASCII source pattern and are not
trimmed. Encoding Values contain capabilities and must never be logged.
Progress notes and finish output/error must pass the separate outbound scrub
before encoding. This module neither implements nor claims to enforce that
scrub; integration must not send raw provider text through these functions.

Decoding contract
-----------------
Each decoder first requires an application object without a top-level refusal.
Success then requires operation-specific fields, types, identities and states;
arbitrary objects, including an object containing only ok:true, are not success.
A present ok field must be true; false, null or a wrong type contradicts success.
Only attach requires that the flag be present. The codec neither fabricates a
missing flag nor modifies the public envelope.

decode_dispatch validates original jobId, boolean created and the job-state
vocabulary. Created jobs must be reserved with a nonempty opaque capability;
they yield JobAuthority. Existing jobs must have absent or null capability and
yield only jobId/state. No replay recovers authority or permits another spawn.

decode_attach(source, job_authority, expected_resumes_job_id) additionally requires
ok:true, original matching job id, nonblank authoritative task, role/lane/base/head,
required nullable work/review/question ids, a positive integral safe deadline,
and required nullable resumeFrom. A resumed brief must name the expected prior
job, a providerRunId, and explicit worktree null or a valid path/branch pair.
Unexpected, missing or mismatched resume data is Protocol. Returned task bytes
are preserved; the dispatch ceiling is not imposed on a cloud-built brief.
Consumers must reconcile returned metadata with their selected role and dispatch
context before execution. Provider, role and resume policies are not implemented.

decode_progress requires matching original job id and a positive safe deadline.
decode_finish requires matching id, a finish-produced state and explicit subject
null or an object with an original id and a known observed job state. The subject
uses the full core state vocabulary, not a verdict-derived transition rule. A
cancelled subject is preserved unchanged. A completed report can yield
review_pending or failed; no local settlement or retry policy is inferred.
decode_cancel requires matching original id and cancelled state.
decode_register requires boolean created, original requested mission/repo and
catalog registeredAt/registeredBy. registeredBy is received metadata, never
injected. Public registration does not require ok. Integer decimal notation is
accepted without coercing strings/fractions or allowing unsafe JavaScript integers.

Reply preserves attention or attentionError independently of mutation success.
A valid attentionError, including INTERNAL, is not a refusal of the preceding
mutation. Absent optional attention stays absent; malformed/null or contradictory
attention fields are Protocol. Attention's domain interpretation is not duplicated.
Reply and text-bearing result types have no generic Debug/Serialize.

decode_rpc validates a complete JSON-RPC reply's version/id, exclusive result/error,
MCP content/optional metadata and structuredContent. Integral numeric RPC codes,
including decimal notation and numbers beyond i64, yield CloudError::Rpc. Missing
structuredContent has no text-parsing fallback. An operation-specific decoder
must still accept the application object before success is established.

Only complete source schema/auth/domain nonmutating envelopes become Refused.
Generic isError, malformed or contradictory envelopes, INTERNAL and availability
failures become Protocol. Both Protocol and Rpc retain Unknown mutation outcome,
as does transport/HTTP loss in frozen types. No retry or safe-replay decision is
implemented. Diagnostics retain no arbitrary error messages or recovery strings.

Integration blockers
--------------------
Production execution module/commands remain intentionally unregistered. Transport
must supply raw replies to decode_rpc or raw HTTP application objects to the
operation decoders. forward.rs currently unwraps JSON-RPC and sanitizes generic
results; blindly reusing it for capability-bearing replies is not validated.
The generated MCP catalog exposes neither progress nor registration tools; HTTP
progress does exist. These codecs do not add tools or automatic registration.
There is no new-mission policy, capability persistence, heartbeat scheduling,
worker spawning, scrub integration, cancel process control or retry reconciliation.
No primary checkout edit, real store/config/credential access, provider/cloud
call, install, release, deployment, migration, main merge or push was performed.
No commit is made: staged delivery is a deliberate handoff, not a tool denial or
claim of user authorization. Commit/landing and runtime acceptance remain separate.
