Pure API and integration contract
---------------------------------
scrub_text(value, known_secrets) -> ScrubbedText:
  Full text, with no size truncation. Nonempty known secrets are replaced
  literally, in the provided order, before the five source patterns:
  private-key blocks; secret-named assignments; Bearer/Basic; vendor tokens;
  opaque runs of at least 40 ASCII characters with lower, upper and digit.
  Replacement is [REDACTED]. Short known secrets are not silently skipped.
  JavaScript ASCII word boundaries and its four line terminators are retained.
  PRIVATE_KEY retains source semantics, including unmatched blocks remaining
  visible and nonmatching BEGIN/END key-type labels still closing a block.
  ASSIGNMENT is widened only to an optional Bash: prefix at line/command start
  (with source case-insensitivity), not assignments anywhere in prose. Thus
  Bash: KEY=value is masked, while Bash: echo KEY=value is not an assignment
  match. This is the reviewed OD15 divergence, not shell parsing.

scrub_outbound(OutboundText { note, finish_output, finish_error }, known_secrets)
  -> Result<ScrubbedOutbound, ScrubError>:
  One gate handles every optional surface and preserves absent values. Future
  outbound integration must use it before request serialization or logging;
  this lane does not edit or implement those senders. No finish text is clipped
  at 8,192 or at the cloud's rejection ceilings. JSON-bearing full text is
  decoded for one layer before masking. Outbound TEXT also masks decoded keys
  with the full known-secret/five-pattern policy. Changed JSON is reserialized,
  then ALWAYS passed through the full text gate, including numeric scalars.
  Unchanged decoded content retains its original formatting and passes through
  the same text gate. This does not change the separate JSON Value APIs.
  Text is not promised to remain parseable JSON: replacing a known numeric
  secret with [REDACTED] is necessary for outward TEXT, not a Value conversion.
  JSON-shaped means the first character after Unicode whitespace or BOM is
  {, [ or a quotation mark. A decoder failure on this path rejects the entire
  outbound batch as ScrubError::InvalidJson, with no partial successes or input
  retained. This covers malformed JSON, unsupported lone surrogates and the
  established serde_json nesting limit. No custom parser or limit bypass is used.
  Non-JSON-shaped ordinary prose deliberately uses literal text matching;
  JSON-looking content embedded later in prose is not decoded. Standalone valid
  scalars are decoded too. Bracket/quote-prefixed diagnostics that are not valid
  JSON therefore return the same safe category rather than a weaker success.
  JSON key masking and decoded-surface behavior deliberately extend the plugin's
  text-only function, following forward.rs. This is not recursive decoding of
  embedded JSON documents inside strings.

scrub_json(value, known_secrets) -> Result<serde_json::Value, ScrubError>:
  Decode JSON escapes, then mask structural secret fields and text strings.
  Arrays/scalars are preserved; known secrets in keys are masked too, as in
  the CLI helper. Key collisions after masking follow Value's map semantics.
  Parser failures yield only ScrubError::InvalidJson: no input, parser message,
  path, arbitrary provider error or credential is retained in the category.
  Malformed JSON and unsupported lone-surrogate JSON strings are rejected.
  The existing serde_json nesting bound applies; no limit knob is introduced.

Separately named bounded source operations
------------------------------------------
scrub_note_line_utf16_200(value, known_secrets) -> Option<ScrubbedText>:
  The plugin's storage/jobs.ts recordProgress operation: scrub first, collapse
  JavaScript whitespace, trim, keep the first 200 UTF-16 units, omit an empty
  note. This is not the cloud's 500-unit validation policy. JSON-bearing notes
  must first pass the outbound gate; this helper reproduces the source's plain
  note normalization and is not an alternate outbound transport gate.
scrub_transcript_json_utf16_8192(value, known_secrets) -> Result<Value, ScrubError>:
  The plugin's transcript operation: scrub every string before keeping an
  8,192-UTF-16-unit prefix. The historical suffix says
  [truncated, <scrubbed UTF-16 length> bytes total]. The word bytes is retained
  from the source even though the number is not a UTF-8 byte count. This API
  must not be substituted for finish output/error or ordinary outbound notes.

Measured Unicode differences, not silent corrections
-----------------------------------------------------
JavaScript value.length and slice count UTF-16 units, despite the source
constant MAX_STRING_BYTES. All bounds above explicitly name UTF-16.
  8,192 copies of U+00E9: 8,192 UTF-16 units, 16,384 UTF-8 bytes; not truncated.
  8,191 copies of U+00E9 + an astral emoji + z:
    8,194 UTF-16 units, 16,387 UTF-8 bytes. JavaScript slice(0,8192) ends on a
    lone high surrogate. Rust strings cannot contain it: this bounded API
    explicitly represents it as U+FFFD, not by rounding to a scalar boundary.
  199 copies of a + an astral emoji + z:
    202 UTF-16 units, 204 UTF-8 bytes. The note's 200-unit prefix similarly
    ends with U+FFFD instead of JavaScript's lone surrogate.
JSON oracle comparison separately counts these two surrogate normalization
cases; equality is not asserted over unsupported JavaScript string states.
The full-text operation never introduces this lossy cut.

secret discovery, memory zeroization or hostile same-UID isolation. Unmatched
private keys, arbitrary encodings and JSON documents embedded inside strings
remain outside the five-pattern promise. Do not log raw OutboundText or claim
that the ScrubbedText type certifies all secrets are absent.
